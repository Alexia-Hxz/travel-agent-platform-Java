## 4. 已知差异（4 条，均有理由）

1. **视觉模型名**：原项目写死 `qwen3-vl-flash`，该模型在 DashScope 上已不存在
   （实测 `404 model_not_found`）。改为 `qwen3-vl-plus`，可用 `VISION_MODEL_NAME` 覆盖。
2. **向量后端**：R5 选定 Milvus。Milvus 实现已写完并编译通过，但本机 Docker Hub 不可达、
   minio 镜像被镜像站拒绝，**未能做连通性验证**。因此加了 `MysqlVectorStore`（精确余弦，
   与 Chroma 的 `1-distance` 数学等价），配置 `app.vector.backend`：
   `auto`（默认，先试 Milvus 失败回退并 WARN）/`milvus`（严格）/`mysql`。
   本机所有检索验证走的是 MySQL 路径。
3. **422 结构**：业务错误一律 `{"detail":"中文"}`；Bean Validation 失败按 FastAPI 的数组结构
   （`type/loc/msg`），不含 `input` 字段。
4. **规划器内部实现**：原 LangGraph 的纯线性 DAG 用 Service 顺序调用 + 共享状态对象实现，
   节点顺序、事件名、`phase/progress` 数值与原实现一致；图片仍走独立线程并在 compose 阶段 join。

### 7.1 图片（迁移后补修）

迁完第一次打开时，行程里的地点卡片只显示分类图标。原因不是前端：旧库
`places.image_url` 存的是 `http://127.0.0.1:8001/static/place_images/cache/<sha>.jpg`，
而**这些缓存文件还在 Python 项目的 `app/static/place_images/cache/`**，Java 这边没有，
请求 404 后前端按设计退回占位图。

`tools/restore_place_images.py` 做了三件事：

1. 复制 150 个缓存图片到 `backend/data/photo-cache/`（`/static/place_images/cache/**` 映射的目录）；
2. 把 21 条旧绝对地址改写成相对路径 `/static/...`（换端口也不会坏）；
3. 把 23 条 Pexels 外链镜像到本地（下载失败保留原链接）。

结果：61 个地点里 **60 个有本地图片**（33 家餐厅 + 27 个景点全部有图），**只有 1 家酒店无图**。
酒店不配图是原项目的刻意设计（"一张别的酒店的照片不提供任何信息"）。

`tools/backfill_place_images.py` 给迁移时仍为空的地点补图：让模型生成**英文**检索词
（图库按英文索引，中文名会搜到别处；餐厅优先用招牌菜/菜系）→ Pexels 搜索 →
可达性探测（真取前 64KB）→ 下载到本地缓存 → 写相对路径。酒店一律跳过。
踩到的两个坑已写进代码注释：Pexels 会对默认 `Python-urllib/3.x` 返回 **403**（必须带 UA），
带 `Content-Type: application/json` 的 GET 会被回 **400**。

`tools/check_image_chain.py` 是可重复的回归：建临时行程 → 写 `image_url` → 读回来 →
真的 GET 一次，确认 200 且是图片。

### 7.2 端口占用导致的"数据对不上"

排查图片时发现 8001 上跑的是 **Python 的 uvicorn**（响应头 `server: uvicorn`），不是 Java：
14:13 有人双击了 Python 版的启动脚本，它抢走了 8001，于是"旧图能出、新图 404"。
`stop-all.bat` 现在会同时清理 `uvicorn` 进程；`start-backend.bat` 发现 8001 被占用会给出提示，
避免两个版本悄悄互相顶替。

## 8. 面向用户的文案

后端返回给前端的所有提示已全部中文（原实现里有一批英文，如
`Trip does not exist.` / `Only JPG, JPEG, PNG, WEBP, and PDF files are supported.` /
`Planning job does not exist.` / `Internal Server Error`），替换后冒烟用例同步更新，
并新增了两条「错误响应必须是中文」的断言。

需要说明的一点：浏览器在**完全连不上后端**时显示的是浏览器自己的 `Failed to fetch`，
这句话由浏览器生成、不经过后端，前端源码又要求一行不改，所以只能在启动脚本层面避免——
`启动旅迹AI(JAVA).bat` 现在改为**轮询 `/api/v1/health` 返回 200 才打开浏览器**，
而不是"端口在听就算好"。实测 12 秒就绪。

## 10. 2026-10-24 对齐补丁（第二轮）

第一轮验收只覆盖了接口形状，没有覆盖 AI 结果的内容。对照 Python 源码又修了以下差异：

- **轮询卡片分类**：`PlanningJobService` 的快照把 `category` 当成 `type` 读，导致规划进行中
  酒店/餐厅卡片全部落进"景点"组；`price_pending` 也被写死成 `false`。
- **调整预算**：预览里的"保留项"缺 `quoted_cost`/`price_level`，已按类别默认价计费；
  现在与 Python 一样按用户同意的报价计。
- **单日规划**：`mode=day_plan` 只加不删，应用后同一天会出现两份行程；现在按 Python 的
  `day_operations` 先删当天再排 5 个时段。
- **最终总结**：`PlanSummaryGenerator` 用裸 `ObjectMapper` 序列化含 `LocalDate` 的上下文，
  失败后降级成 `Map.toString()`；现在注入 Spring 的 `ObjectMapper`。
- **调整草案**：`sources` 恒空、上传资料没有进入模型上下文、空 `instruction` 会 NPE 500、
  非法 `mode` 被静默忽略——都已修复（`sources` 现在返回收藏地点 + 联网结果）。
- **推荐引擎**：补上分类覆盖（每类最多 3 轮）、8 并发比价、酒店评分/房价与招牌菜补全、
  价格档位铺开、外币换算/当地下限/免费识别/超预算阈值，以及"负担得起的排前面"。
- **分类预算**：`BudgetPlanGenerator` 让模型给份额，失败才回落默认份额（`source` 不再恒为 `default`）。
- **图片**：接入 TheMealDB 菜图、按菜系选 `restaurant_*.svg` 占位图、给已排行程地点配图，
  并把图片回填进 `daily_plan`。
- **调整理解**：补上暴雨/闭园/交通中断的室内替代时间线、主题乐园半小时时间线、
  "12月3日/第3天"自然语言日期、"预算 + 其它要求"合并解析、替换候选名取自真实地点。
